# Bounded adaptive-concurrency ablation

The experimental `ratio-v2` and `gradient-candidate-v2` methods are engineering
candidates. They do not replace v1 or the default PAARC controller. The scientific
question is whether feedback can find a useful setting, and separately whether
actual HTTP activity can sustain 150 requests on the selected TaiBIF workload.
Neither outcome is assumed. Application first-body delay is not packet RTT.

## Decision rules

Both v2 methods default to a one-second tick, five eligible observations in a
two-second window, a five-second stale-sample gap, and a 120-second baseline age.
The baseline is the observed p10 delay, refreshed at two permits after expiry;
a one-second probe and elapsed-time exponential smoothing are retained.
Initialization is still configured by `C_init`, never by the 150 target.
Overload has priority and halves the limit; smoothed excess delay of four times
the baseline also halves it. These safeguards survive mechanism ablations.

An instantaneous permit-utilization gate (inflight at least 0.8 of the current
limit) controls positive growth. During startup, grow by ceil(C × multiplier),
limited to +64 per tick. Exit startup when smoothed delay reaches target ratio ×
baseline. Three falling-gradient ticks can rearm startup; a baseline probe also
rearms it. No growth occurs on empty, sparse or stale observations.

Ratio then computes `floor(C × clip(sqrt(target_delay/current_delay), .85, 1.10)
+ 1)`. Gradient decreases by .85 at the delay budget, or after two persistent
normalized gradient observations >= .25/s, holds at >= .1/s, otherwise grows by
`min(8, ceil(.02*C))` when utilized. Every result is clipped to configured bounds.
Gradient derivative is the change in smoothed excess delay divided by elapsed
seconds and the delay baseline. Recovery grace defaults to one second.

V2 `method_options` expose `startup_growth_factor` (1 < x <= 2),
`startup_max_step` (positive integer), `target_delay_ratio` (1 < x < 5), and
`utilization_threshold` (0 < x <= 1). Existing timing/sampling options remain
explicit. V1 rejects these new options rather than silently ignoring them.

## Prospective matrix and limits

The frozen protocol is generated by `benchmark.real_server_study.ablation`:

- 24 native controlled cases: two methods × six variants × two conditions.
  Variants remove startup, use ten-second refresh, remove utilization gating,
  remove elapsed smoothing, or remove method feedback, plus full control.
  No-method-feedback removes Ratio's ratio or Gradient's soft delay/gradient
  decisions; common hard overload/delay safeguards remain. Known byte truth,
  origin admission audit, 4→1→4 realized capacity and a separately paced sparse
  episode establish which mechanisms actually ran. Normalized capacity is not
  evidence of 150-request capacity.
- Two public pipeline diagnostics: tasks/permits 256 versus 512 with TCP/actual
  HTTP ceiling256. This joint change cannot isolate tasks from permits.
- Sixteen screens: full 2³ startup1.25/1.5, baseline10/120 seconds, target2/3,
  separately for each method. Screening is exploratory without replication.
- Eighteen validation slots: three independent blocks of v1 controls and each
  method's balanced and 150+ selections. Identical selected configurations alias
  one execution per block and are not independent replicates. No feasible
  selection leaves its slots visibly unstarted.

All arms start at four, minimum two, internal ceiling512, except the explicitly
fixed capacity diagnostics. All use TCP ceiling256. Screening network windows
are120 seconds with evaluation20–60; others180 seconds with evaluation30–90.
150 qualification requires backlog throughout evaluation, at least90% of time
at150 actual HTTP requests, and one continuous30-second span. Balanced selection
requires median delay <=3× initial low-load baseline. All selection requires
>=99% verified credit among dispatched terminal rows and no failed warning response.
Select the lowest actual median among settings within5% of the best verified
evaluation-window goodput, then lower p95 delay, then identifier. Three of three
held-out windows must qualify for a replicated150 result. Report ordinary paired
run-level intervals and missing pairs; no universal superiority/optimum claim.

Frozen TaiBIF URL populations are disjoint across capacity, tuning and validation.
Arms within a stage use matched manifests; cache state is not guaranteed cold.
There is no cache busting, success selection, retry or extra scientific attempt.
Processing reservations are420 seconds per screen and600 per capacity/validation
run, including the unchanged120/180-second network windows. Retained8192-row
evidence took about45 seconds of networking,44 of native finalization and50 of
independent verification. The original300/480-second reservations could truncate
larger successful prefixes. These prospective ceilings reserve processing time
within the same eight-hour/global campaign limits; they authorize no extra
traffic, run or VM window. Admission may leave later slots unstarted if actual
processing or provider delays consume the finite envelope.
A3× delay warning tests downward response within2 ticks. Three ten-second bins
at5× baseline stop an arm. Only latency stops permit a ten-minute cooldown and
one predefined low-load recovery (>=95% valid, median <=1.5× initial baseline).
At most three cooldowns. Access refusals,429/503,TLS and integrity failures end
public-host testing. Delay alone does not identify a server quota.

## Execution and accountable window completion

The explicitly selected `bounded-adaptive-ablation-v1` profile permits32768
original rows,6GiB bodies,128MiB metadata,16GiB artifact and one attempt per row.
It alone drains owned work for up to30 seconds and archives a verified prefix
on shutdown. The native full-manifest completion flag remains false. The study
verifier separately recognizes protocol-window completion, reconciles all
original rows, and accepts only exact guard-proven planned admission rejections.
Exact planned body/admission censoring is reported separately and excluded from the terminal-row success constraint; it remains in original-row coverage. Unknown interruptions earn no credit. V1 record interpretation is unchanged.

The cloud bridge uses the established trusted manager/worker/origin topology and
supervisor, preserving accounts, grants and cleanup obligations. It admits at
most8 one-hour windows and300 new conservative SUs within8 hours, including
cleanup, audit, collection and reporting. It uses one new384GiB identified volume
and preserves older volumes. Aggregate limits:1.2M public request intents,
200GiB bodies,256GiB artifacts,40GiB free reserve,4GiB compressed metadata,
1200-second offline audit and900-second collection. No supervisor restart or
account reset is part of this study. Provider failures retain cleanup obligations.

Source, input, configuration, selection and lease identities bind each first
attempt. Each run is verified once and journals are sealed into a lossless bundle.
Aggregate auditing checks receipts/digests/arithmetic, resumes unchanged archive
units and never reruns acquisition. Compressed transfer uses one file per run,
with bounded expansion and digest-checked local extraction. Retained third-party
payloads stay on the campaign volume; the private report is built from metadata.

Implementation, local qualification, branch CI and at most two independent static
review invocations precede activation. The maintainer authorized this study to run
before one final PR. No PR is opened until science, audit, report and cleanup
finish; human merge remains required. No default promotion or submission
readiness follows from these exploratory experiments.
